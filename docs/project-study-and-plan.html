1 الملخص التنفيذي

منصة EduAI هي منصة تعليمية ذكية عربية (مشروع تخرج) متكاملة ومُنتجة، جمعت بين المحادثة التوثيقية (RAG)، والتلخيص والخرائط الذهنية، واستوديو الاختبارات، والتدقيق الأكاديمي، والترجمة الأكاديمية، ومولّد العروض التقديمية بسير عمل آلي (HTML ← Chrome headless ← PPTX/PDF/PNG).

🔴 الخلاصة بأربع نقاط:
  1. المنتج شبه مكتمل وظيفياً — جميع الأدوات تعمل محلياً، وDeck Studio (نظام الهويات البصرية) متقدم جداً.
  2. الأمان في حالة حرجة — تسجيل دخول بلا كلمة مرور (student-login)، وترقية ذاتية للمستخدم لدور admin عند التسجيل، وهيوية X-User-Id قابلة للتزوير، وفتحة في تحقق Google JWT.
  3. جودة الاختبارات صفر — لا pytest ولا vitest ولا ruff، وCI «يبتلع» الأخطاء عبر || true فلا يفشل أبداً.
  4. مسارات العمل الثلاثة فروع فارغة — «الفرق» لم يبدأ أي مهمة فعلية بعد؛ الفروع موجودة لكنها نسخ من main بلا أي كود.

هذه الدراسة أُعدّت عبر ثلاث زوايا بحث متوازية (باك إند، فرونت إند، تاريخ git ومنهجية الفريق) ثم دُمجت في هذا المستند. الخط الموصى به: إغلاق الثغرات الحرجة أسبوعياً قبل أي ميزة جديدة ثم رفع الجودة بالاختبارات ثم تمكين التعاون الجماعي والنشر.

3.2 مسار البيانات الرئيسي (RAG)

  1. POST /api/upload ← DocumentService.extract_text_and_pages (حسب الامتداد) ← chunk_document(250 word, overlap 50) ← حفظ في documents.chunks_json.
  2. POST /api/chat / /api/chat/stream ← RAGService.search_relevant_chunks (≤100 قطعة: يعيد الكل؛ >100: TF-IDF أو كلمات مفتاحية) ← AIService.answer_with_rag(_stream).
  3. الإجابة تُعالَج بـ sanitize_text (إصلاح hallucinations معروفة، تجريد GS الفرق في الترميزات، ترقيم الاقتباسات) وتُعرض مع [المصدر: صفحة N].

3.3 مسار العروض (Deck Studio)

  1. POST /api/presentations/generate ← PresentationService.create → generate_deck (AI ينتج JSON وفق 8 قوالب شرائح).
  2. المستخدم يعدّل الـ Deck JSON عبر PUT /api/presentations/{id}/deck.
  3. POST /api/presentations/{id}/render ← render_deck ← subprocess engine.py: build HTML → Chrome screenshots → python-pptx + PIL PDF.
  4. الهوية البصرية (قالب أو مولّد أو مستورَد من PPTX) تُحوَّل إلى _identity_css_override لتصبغ كل الشرائح بالـ CSS variables.

3.4 نقاط القوة المعمارية

  • فصل واضح: routes / services / database / presentation_engine.
  • دعم متعدد المزودات عبر execute_chat_completion (Gemini ↔ OpenAI-compatible) مع تجربة اتصال (/api/validate-key, /api/fetch-models).
  • محرك عرض كامل منظّم بالمعاملات: القالب + colors/fonts/accent → CSS override → تلوين شامل.
  • قاعدة بيانات صريحة مع تجزئة كلمات مرور pbkdf2_sha256$150000$… وترحيل تلقائي للقديم.

6 محرك العروض (Presentation Engine / Deck Studio)

أكثر مكوّن تقدمّاً وتمايزاً في المشروع، أُنشئ مؤخراً (2016-09-07، الالتزامان 1b7ff06 و7d5b0cb).

6.1 كيف يعمل

  1. التوليد بالذكاء: PresentationService.generate_deck يطلب من LLM JSON وفق 8 قوالب شرائح (cover/content/twocol/stats/chart/timeline/table/closing) مع قواعد جودة وwhitelist للأيقونات والفنون.
  2. الهوية البصرية: نظام templates في DB + generate_template_theme (AI) + extract_pptx_theme (من ملف PPTX) + تسجيل ألوان/خطوط/accent.
  3. الرندر: engine.py يحوّل الشرائح إلى HTML (قوالب academic / dark-tech + CSS override للهوية المخصصة)، ثم Chrome headless يلتقط PNG بدقة 2560×1440، ثم python-pptx يجمعها في .pptx وتخرج .pdf متعدد الصفحات عبر PIL، ويمكن تنزيل ملف مصغّرات PNG مضغوطاً.
  4. الفن: artgen.py يولد 15 خلفية (gpt-image-1) أو صوراً بديلة Pillow؛ يُربط صبغ الهوية عبر --art-tint (الأولوية T3.2).
نقاط ضعف قائمة: (G9) خلفيات art لا تُصبغ حالياً بألوان الهوية؛ (G10) الترجمة/التلخيص تُقتطع عند ~8000 حرف؛ (G3) لا قفل على الرندر المتزامن لنفس العرض (TOCTOU).
